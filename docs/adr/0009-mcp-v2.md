# ADR 0009: MCP v2 — a safe control-plane core, transport-agnostic

Status: Accepted
Date: 2026-09-04

## Context

`internal/mcp` was an 8-line doc-only stub. The spec asks for MCP to
become "une interface de contrôle sûre" exposing 11 tools (8 read-only,
3 mutating, 1 privileged) under explicit scopes, with every mutating
call passing through:

```
Authentication → Authorization → Policy → Scope validation →
Rate limiting → Audit → Execution
```

and an explicit warning: "Ne jamais faire confiance à un agent IA
simplement parce qu'il connaît le nom d'un tool MCP." An LLM/agent
calling `cerberus_execute_remediation` must never reach a privileged
action just by knowing that name exists — the safety boundary has to
be enforced by something other than the caller's own claims.

At the same time, no MCP transport (stdio/HTTP) exists yet, and this
codebase's own conventions (see ADR-0006/policyengine, ADR-0005/risk)
favor building the safe, explainable core first and deferring wiring
into a real transport/protocol library until there's a concrete
consumer.

## Decision

`internal/mcp` implements the tool-dispatch core only — no transport,
no protocol library, no privileged credentials:

- **`Tool` interface** (`Name`, `RequiredScopes`, `AllowedArguments`,
  `Handle`) — one small type per MCP tool. `RequiredScopes` and
  `AllowedArguments` are declared by the tool but *enforced* by
  `Server`, never trusted from the tool call itself.
- **`Principal{ID, GrantedScopes}`** — the only source of truth for
  authorization. Authentication (verifying who this is) happens
  upstream, in a future transport; this package's contract starts at
  "I already have an authenticated Principal."
- **`ToolCall.RequestedScopes`** is informational/logging only. It is
  never consulted by `Dispatch` — a caller cannot grant itself a scope
  by asking for it in the request. This is the concrete mechanism
  behind "never trust an agent because it knows a tool name": knowing
  `cerberus_execute_remediation` exists, or even claiming
  `remediation:execute` in the call, does nothing without that scope
  being present on the authenticated `Principal`.
- **`Server.Dispatch`** runs the six-stage pipeline centrally, in one
  place, for every tool, rather than each tool re-implementing its own
  checks (which is exactly how these checks get forgotten on tool #9):
  1. **Authorization** — `Principal.GrantedScopes` must cover
     `Tool.RequiredScopes()`.
  2. **Policy** — calls `policyengine.PolicyEngine.Evaluate` with
     `Domain: "mcp", Action: "mcp:tool:<name>"` (see ADR-0006). A
     `PolicyDecision.ApprovalsRequired > 0` is treated as "not
     executable yet" — `PolicyEngine` only decides the count, it never
     tracks approvals, so `Dispatch` cannot treat `Allow: true` there
     as "proceed."
  3. **Scope validation** — every argument key in the call must be in
     `Tool.AllowedArguments()`; anything else is rejected before
     `Handle` ever sees it. This is the mechanism that keeps mutating
     tools ID-shaped (`finding_id`/`credential_id`/`incident_id`/
     `remediation_id`) rather than accepting a raw secret value by
     accident — a stray `secret_value`/`api_key`-named argument simply
     isn't in any tool's allowlist.
  4. **Rate limiting** — a per-principal token bucket
     (`internal/mcp/ratelimit.go`, stdlib `sync`+`time` only).
  5. **Audit** — recorded via `internal/audit.Sink` (reused as-is —
     already exists, already secret-free by contract) *before*
     execution, so a denied call is audited exactly like a successful
     one, not only on the happy path.
  6. **Execution** — `Tool.Handle` runs, only after all five prior
     stages passed.
- A denial is always a `ToolResult{IsError: true, ErrorMessage: ...}`
  with a non-empty reason — never a raw Go `error` a transport might
  serialize verbatim — matching this codebase's established
  explainability invariant (`Signal.Reason`, `RiskFactor.Reason`,
  `PolicyDecision.Reason` are all always non-empty; MCP denials now
  are too).
- **No MCP protocol SDK was added.** This package is deliberately the
  safe core a stdio/HTTP transport will wire into later — `Dispatch`
  takes a plain `Principal`+`ToolCall` and returns a plain
  `ToolResult`, with no framing/serialization concerns. `cmd/cerberus/
  mcp.go` is untouched by this change; wiring a transport to this core
  is separate, later work.
- **`cerberus_execute_remediation` is deliberately inert.** It requires
  `ScopeRemediationExecute` and runs through the identical pipeline —
  nothing is special-cased to skip a stage for it. Its `Handle` reports
  "no approved plan or Executor is available" rather than performing
  or simulating any action, because this package holds no cloud
  credentials and no `remediation.Executor` is wired in (Phase K,
  ADR-0003). Building that pipeline around a currently-inert privileged
  tool — instead of adding the pipeline later once the tool "does
  something" — is intentional: the safety boundary should never be a
  retrofit.
- **`cerberus_request_remediation`** similarly only accepts a
  `credential_id` and returns an honest "not wired" result:
  `remediation.Planner.Plan` takes a finding ID today, not a credential
  ID, and no `Planner` implementation is injected here. Fabricating a
  fake `Plan` would be worse than reporting the gap.
- **`cerberus_start_scan`/`cancel_scan`/`get_scan`** are honest stubs
  for the same reason: no scan-run store exists yet
  (`internal/queue` is a bare publish/consume primitive, not a job
  tracker) — a scan ID with nothing behind it would mislead a caller
  more than an explicit "not implemented."
- **Fully real today**: all 8 read-only tools
  (`cerberus_list_findings`, `get_finding`, `explain_finding`,
  `list_credentials`, `get_credential`, `list_incidents`,
  `get_incident`) except `get_scan`, backed directly by the existing
  `findings.Store`/`credentials.CredentialStore`/`IncidentStore`
  interfaces — and the pipeline itself.
  `cerberus_explain_finding` returns `Finding.Provenance` unchanged —
  the same data `cerberus scan file --format explain` renders — rather
  than recomputing an explanation, so the CLI and MCP surfaces cannot
  drift apart.

## Consequences

- Every future tool (GitHub/GCP/Vault remediation, a real scan
  orchestrator) gets the six-stage pipeline for free just by
  implementing `Tool` and being registered with `NewServer` — there is
  no way to add a tool that skips authorization/policy/audit, short of
  bypassing `Dispatch` entirely.
- `PolicyEngine`/`RateLimiter`/`audit.Sink` are all injected
  dependencies, so wiring `internal/mcp` into `cmd/cerberus-mcp` later
  only requires choosing concrete implementations (the `NativeEngine`
  from ADR-0006, a real audit backend once one exists beyond
  `NopSink`) — no changes to this package's logic.
- The trade-off is that this slice is not yet reachable from any
  transport — `cerberus mcp` in the CLI still reports "not
  implemented." That wiring, plus the actual stdio/HTTP protocol
  framing, is explicitly out of scope here and left for the next step.

## Alternatives considered

- **Per-tool authorization/policy/audit checks** — rejected: this is
  exactly the "dozens of scattered `if`s" pattern ADR-0006 already
  rejected for policy; doing it per-tool for MCP specifically would
  make it trivial to add tool #12 without remembering the audit call.
- **Trusting `ToolCall.RequestedScopes` as the authorization source**
  — rejected outright: this is the literal failure mode the spec warns
  about ("un agent IA... connaît le nom d'un tool MCP"). Scopes must
  come from something the caller cannot forge — the authenticated
  `Principal` — not from the request payload.
- **Adopting an MCP protocol SDK now** — rejected for this slice: no
  transport exists yet to justify the dependency, and the safe
  dispatch core is valuable and testable on its own, independent of
  which transport eventually calls it (stdio today, HTTP+auth later
  are both plausible — the core shouldn't need to change either way).
- **Implementing `cerberus_execute_remediation` against a mock/no-op
  "success" result** — rejected: a tool that always reports success
  would be indistinguishable from a working one to a calling agent,
  defeating the entire point of keeping remediation privileged and
  separate (ADR-0003). An honest "not wired" error is safer than a
  convincing fake success.
